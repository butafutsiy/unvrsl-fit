# UNVRSL FIT v392 – техническая доработка

База: `main`, `09eaa08` (v391). Изменения выполнены в существующем репозитории `butafutsiy/unvrsl-fit`. Отдельный сайт не создавался. Статус: код и автоматические проверки готовы к проверке в draft PR; релиз пока не удовлетворяет всем критериям исходного задания.

## 1. Причины

- Завершение подхода определялось несколькими обработчиками. Проверка положительного веса блокировала собственный вес 0.
- Сохранением результата управляли несколько обёрток. Ошибка облака могла сопровождаться очисткой активной тренировки.
- Полное состояние сериализовалось периодически; резервные снимки могли возвращать старое состояние поверх актуального.
- Фактически используемый таймер жил в sessionStorage и загружался отложенно по старой версии URL. Основной таймер и новый таймер имели разные состояния.
- Каталог строился несколькими слоями, включая внешний JSON 17 391 530 байт; анатомический модуль дополнял утверждённую базу своими записями.
- Два модуля анатомии меняли один DOM. Повторная запись идентичной разметки запускала MutationObserver снова.
- Несколько алгоритмов независимо рассчитывали вес, 1ПМ и итог. Фазы UNVRSL из конструктора (`role`) не участвовали в сравнении истории.
- Нулевой ручной вес терялся также при классификации программы и в свободной тренировке, где 0 означал автоматический режим.
- Service worker очищал кеш и работал только через сеть. Часть динамических загрузчиков сохраняла старые версии URL.
- Облачная история читалась без постраничной загрузки и повторно отправлялась целиком.

## 2. Удалённые и отключённые реализации

Удалены дубли `editSet`/`toggleSet` в `og-core`, старые владельцы завершения/итогов в smart-training, advanced-training, cloud и cloud-patch, агрегатор рекомендаций из unvrsl-method, периодический механизм восстановления старых снимков persistence-safety. Убраны динамическое дополнение каталога из anatome-local и запуск цепочки quality/strict/additions для основного каталога.

Из действующего графа исключены performance-control, machine-weight-adaptation, workout-weight-integrity и старые подмены медиа hip/barbell. Удалён отложенный загрузчик rest-timer из workout-duration. Некоторые исторические файлы и совместимые имена функций остаются в репозитории, но не являются владельцами новых экранов. Полное физическое удаление всех исторических файлов не выполнено.

## 3. Активная тренировка

`workout-store.js` хранит полный снимок под тем же `activeWorkoutId`, с владельцем и схемой 4. Основное состояние сохраняется в существующем ключе `unvrsl-fit-v3`; отдельный журнал `unvrsl-active-workout-v4` содержит черновики по владельцам и отметки завершения/удаления. Миграция добавляет идентификаторы и типы, сохраняет остальные данные и допускает повторный запуск.

Запись происходит на вводе, изменении подхода, таймера и позиции. IndexedDB служит резервным зеркалом. Старое зеркало используется только при отсутствии основного состояния. Закрытый черновик не восстанавливается из устаревшего снимка.

При завершении сначала сохраняется черновик, затем ожидается подтверждение облака, затем фиксируется история и закрывается журнал. Ошибка оставляет черновик; повторная попытка использует тот же ID. Параллельные нажатия используют одну транзакцию. Кнопка «Продолжить» после ошибки возвращает возможность редактировать результат. Удаление требует отдельного подтверждения с заданным текстом. Смена аккаунта архивирует локальное состояние предыдущего владельца.

Это защита от закрытия/перезапуска приложения, а не гарантия восстановления после явной очистки пользователем всех данных браузера.

## 4. Собственный вес и результаты

`workout-domain.js` отделяет отсутствие значения от 0, поддерживает десять типов нагрузки. Для собственного веса дополнительное отягощение 0 допустимо; RPE/RIR необязательны. История показывает собственный вес, дополнительный вес либо помощь отдельно.

Масса тела берётся только из доступной записи на дату тренировки. Без неё объём собственного веса остаётся неизвестным, а повторения сохраняются. Вес гантели не удваивается в 1ПМ; объём учитывает число гантелей. Для веса на сторону нужен подтверждённый множитель и вес конструкции. 1ПМ исключает разминку, незавершённую работу, специальные методы и упражнения с неподходящим правилом результата.

Итог, история результата и картинка используют общий расчёт фактически завершённых рабочих подходов. Неполный объём обозначен явно. Рекорды требуют сопоставимой предшествующей истории и не подтверждаются плановыми значениями. Картинка содержит текущую тренировку, до двух основных результатов и точный PNG-предпросмотр.

## 5. Индивидуальные шаги

Профили лежат рядом с каноническим упражнением, пользовательские изменения – в `exerciseWeightProfiles`. Сохранены исходные различия оборудования: гантели, блоки, штанги, помощь и собственный вес. Есть минимум, шаг, правило округления, ряд доступных весов и предел изменения. Кнопки веса и рекомендации используют общий профиль. Ручные значения защищены флагом `manualOverride` и не заменяются автоматически. Допустимый ручной 0 не превращается в режим «Авто».

Фактический ряд гантелей/стека конкретного зала автоматически неизвестен; его нужно задать профилем. Наличие шага в каталоге не подтверждает оборудование каждого клиента.

## 6. Рекомендации

Единый модуль читает историю по стабильному ID с безопасными алиасами, независимо от программы. Использует несколько последних сопоставимых тренировок, диапазон повторений, усилие при наличии, темп, метод, фазу, тип нагрузки, оборудование и самочувствие. Разные фазы UNVRSL, помощь и добавленный вес не смешиваются. При малом числе сопоставимых тренировок вес сохраняется. Для помощи прогресс уменьшает показание тренажёра. Есть объяснение, доступный шаг, уверенность и основание расчёта; распознаются стабильность и регресс. Следующий подход учитывает фактически выполненный подход сегодня.

Облачные workout-записи загружаются страницами; одинаковые сессии повторно не отправляются. Ручные записи силовых результатов клиентов из отдельной системы измерений не преобразованы в полноценные тренировочные сессии и не выдаются за выполненные рабочие подходы.

## 8. iPhone / Safari / установленная PWA

Физическое устройство недоступно. Браузерный доступ к локальному серверу отклонён средой (`ERR_BLOCKED_BY_CLIENT`). Не выполнены реальные проверки выгрузки iOS, обновления установленной PWA, Web Share, быстрого скролла, сетевого обрыва и live Supabase.

Модель перезапуска без sessionStorage и тесты service worker подтверждают только автоматизированные сценарии, не поведение реального iPhone. Перед выпуском остаётся пройти весь сценарий на устройстве со старой версией и существующим черновиком.

## 9. Производительность

Воспроизводимый стенд: Node/jsdom, локальные ресурсы, один и тот же внешний JSON как fixture, без реальной сети, layout и paint. Исходная версия 09eaa08 не закончила стенд за 30 секунд. Новый результат записан в `performance-after-v392.json`. Это не Lighthouse, не LCP и не замер iPhone; коэффициент ускорения из timeout не вычисляется.

Внешний JSON каталога 17,39 МБ больше не запрашивается. Канонические 188 записей встроены локально. Список выводит 24 карточки с постепенным добавлением; медиа запрашиваются по видимости, GIF вне экрана останавливаются удалением src. Фиксированные квадратные контейнеры используют contain. Поиск дебаунсирован, индекс и история использования кешируются. Статистика и тяжёлые модули загружаются после критической оболочки; повторный вход в каталог сохраняет DOM.

Отдельные реальные замеры вкладки клиентов, сетевой истории и холодного Safari пока отсутствуют.
